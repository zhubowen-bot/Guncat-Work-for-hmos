# 交互模式 · 能力调度档位提示词适配说明

> 本文说明「设置 → 能力 → 能力调度」九个档位的提示词是怎么拼出来的：哪些段**九档完全共用**、哪些**调整后共用**、哪些**只属于轻简档**；八档从聊天引擎迁移进来的成熟提示词，具体改了哪些锚点、为什么改。
>
> 提示词嵌在代码与 rawfile 里，逐字比对很不方便，所以九档**组合后的完整系统提示词**已由导出脚本原样落盘：[interactive-tiers/README.md](interactive-tiers/README.md)。审阅时建议先看本文第三、四节建立骨架，再打开对应档位的导出文件，用 `grep -n "交互模式适配"` 定位所有改动点。
>
> 文中所有字符数、估算 token、工具数、段数均取自 `docs/prompts/interactive-tiers/` 的最新导出或对应代码（出处随文标注），不手工估算；重新导出后以新导出为准。运行时分层细节见[交互模式架构](../architecture/interactive-mode.md#24-能力调度九档位r77当前)。

## 一、这是什么

**能力调度是交互模式的一个设置项**：设置 →「能力」→「能力调度」（`SettingsPage` 的 `tier` 详情页），九档单选，默认「轻简」；选择持久化在 `guncat_interactive_tier`，由 `InteractiveTiers.ALL` 单一事实源驱动设置页、系统提示词、工具面与导出文档。

选一个档位，实际决定三件事：

1. **系统提示词**——共享层（界面语言契约 / 丰富度 / 环境 / 职责）＋该档的**档位主体**（迁入的成熟提示词）。轻简档没有主体文件，它是原交互模式提示词的逐字节复用。
2. **工具面**——基础 27 个工具不变，检索/多阶段档位追加 `record_search`、`todo_write`（轻简与论文转换仍是 27 个）。
3. **推荐思考强度**——切档时把交互模式思考强度同步到该档推荐值（`low` 或 `high`）；之后仍可在模型弹层手动改，不锁死。

**交付形态不随档位变化**：无论哪一档，回答主体都是一份 `guncat-ui lang` 界面程序、程序之外不写文字。档位改变的是「专业内容与流程的厚度」，不是交付通道。

三条使用边界（都来自代码与设置页文案）：

- **只影响交互模式**：`buildWorkSystemPromptFor(mode, tierId)` 与 `toolDefsForMode(mode, ...)` 只在 `mode === 'interactive'` 时读档位；工作模式与聊天模式的提示词、工具面不受影响。
- **下一轮生效**：提示词与工具面按档位在进程内缓存，切档不改写历史；新档位从下一次请求开始使用，切回旧档可复用旧档缓存前缀。
- **缺主体不崩**：某档的档位主体 md 缺失或为空时，`buildInteractiveSystemPrompt()` 回退轻简档，不会交付一份没有业务主体的"空壳档位"。

## 二、为什么做

交互模式原来的系统提示词是 agent loop 架构工程师为「快」写的：默认零工具、一轮直出、思考要短。这套纪律在速度上是对的，但**专业深度、反幻觉体系、领域工作流**不是它的强项——那些能力沉淀在聊天引擎的八份智能体提示词里（3.0-Flash / 3.0-Pro、2.5-lite、论文转换、三个 Srch 检索智能体、LLM 评估；2.5-max 等未选用版本不在此列），由提示词工程师长期打磨。随着聊天引擎逐步淘汰，这批提示词会闲置。

能力调度把它们吸收成交互模式的可选档位。迁移原则只有四条：

1. **主体逐字保留**：原文的角色定义、思维链、执行模式、工具方法论、反幻觉体系、领域工作流、输出模板、知识库全部保留（含标题文字、示例、表格、emoji、错别字），只删除原文的第一个标题型 H1（H1 由代码层档位声明承担），其余 H1 统一降为 H2。
2. **只做交付形态适配**：新增/改写只发生在与交互模式事实冲突的锚点上——交付物、mermaid、提问方式、平台工具、环境假设、硬编码日期。所有改动必须带「交互模式适配」标注，可 `grep` 审计。
3. **共享层不重复原文**：界面语法、组件清单、工作区规则、工具白名单、组件数量口径都只写在代码共享层；档位主体只承担"业务灵魂"。
4. **轻简不迁移**：轻简＝原交互模式提示词本身，组装结果与旧四段**逐字节一致**（有断言），保证默认档行为不变、依然最快。

收益与代价都明确：重档位把成熟的专业流程带回了交互模式，但提示词显著变长、首答变慢（见第九节）。

## 三、分层设计

### 3.1 四层职责（先看这张表）

| 层 | 内容 | 来源模块 | 共用方式 |
| --- | --- | --- | --- |
| **通用层** | 界面语言契约（身份 / 语法 / 组件清单 / 交互闭环 / 流式顺序 / 示例 / 反例）、真实数据纪律、技能极小索引 | `GuncatUiPrompt`、`GuncatUiLibrary`、`SkillDirectoryFormatter` | **九档逐字节共用**（唯一例外是丰富度段里的数量口径，见下行） |
| **长度与多少控制层** | 丰富度：组件选择优先级表 + 分层配方（结构）＋数量口径 | `GuncatUiPrompt.RICHNESS` / `richnessForTier()` | 结构全档共用；数量口径按档替换：轻简「8~14 够用为准」、八档「12~20+ 不设上限」 |
| **行为与表现控制层** | 档位声明（身份 / 第一纪律 / 工具面政策 / 思考政策 / 丰富度口径）、工作区、本档工具面、起手式、职责收尾 | `InteractiveTierPrompt`（轻简各段复用 `PromptBuilder` / `GuncatUiPrompt` 原文） | 同一骨架按档参数化：轻简逐字节复用原段，八档由代码按档生成或换口径 |
| **档位主体层** | 原聊天引擎提示词的业务灵魂：角色、思维链 / 元认知、执行模式、工具方法论、信息质量与反幻觉、领域工作流、输出结构模板、知识库、自检清单 | `rawfile/interactive-tier-*.md` | 每档一份；轻简没有；八档逐字保留 + 锚点适配 |

分层只做一件事：**把"交付形态的规矩"从原文里抽出来放进共享层，让档位主体只保留业务内容**。因此档位主体里刻意不写 guncat-ui 语法、组件清单、工作区路径、工具白名单、组件数量口径——那些共享层已经写了，重复只会让模型在思考里对齐两份说法。

>
> 组件清单由 `GuncatUiLibrary` 的注册表生成：库内共注册 **77** 个组件，**提示词清单可见 75 个**——`FollowUpBlock` / `FollowUpItem` 两项带 `promptHidden`，只做历史消息与外部程序的接口兜底，设计上不写进提示词。清单段当前 8,712 字符（含 `ListBlock` / `ListItem` 所在的「列表与追问」分组）。

顺序本身就是设计：**纪律在最前**（模型顺序读，契约段有 8.7k 的组件清单，纪律写后面等于没写）→ **先立界面规矩，再给语言能力** → **档位主体居中**（它是整段提示词的正中心，引用界面但不受契约措辞影响）→ **环境与工具靠后**（写程序时才需要）→ **职责收尾**并给出回到开头的指针。`test-core.mjs` 有断言钉住这个顺序。

读表要点：

- 轻简 21,770 字符；最重的专家档 84,708 字符（约 **3.9 倍**字符、**5.0 倍**估算 token）。这是"能力厚度"的直接成本。
- 九档共用的 9 个通用段合计 **15,482 字符**（见第四节）：在轻简里占 **71.1%**，在专家档里只占 **18.3%**——越重的档位，共享层占比越低，差异集中在档位主体。

### 4.3 完全不能共用（只属于轻简档）

下面这些是轻简的"快车道宪法"与配套口径。它们与八档的能力型定位正面冲突，**不迁移、也不出现在八档的档位声明里**：

1. **默认零工具、一轮最多 1~2 次、优先只读**——与效率档"该查的一次不少"、法律档"强制多轮实时检索"、专家档"宁可多检索一轮"直接矛盾。
2. **一律不用 `todo_write` / `record_search` / `goal_*` / `schedule_*` / `subagent` 等长程工具**——八档里有四个档位恰恰**追加**了 `todo_write`（专家 / 法律 / 研究 / 评估）或 `record_search`（六个档位），它们需要使用。
3. **思考纪律"短"**：只定界面骨架 → 定数据来源 → 定标题结论，几句话几个短条目——与六档 `high` 思考强度（专家 / 经典 / 法律 / 研究 / 筛滤 / 评估）以及原文的内化思维链冲突。
4. **素材区口径（不是交付区）**：轻简不主动落盘；八档要按原文导出 Word/Excel/PPT，工作区必须是"素材区 + 产出区"。
5. **「典型 8~14 个组件、够用为准」的数量口径**：八档统一换成「12~20+ 不设上限、越多越好」。
6. **轻简的起手式与职责原文**：含"速度与工具纪律以开头那一节为准"的指针，八档改由档位声明裁决。

反向也成立：八档不是"轻简 + 专业内容"的叠加，而是**用各档第一纪律替换快车道纪律**。每档 `tierPrime()` 里的「档位边界与冲突裁决」写明：交付形态、界面语法、组件清单、工具面、丰富度计量以共享层为准；专业方法论、工作流、输出结构、自检与知识库以正文为准；两类冲突分别归各自的家。

## 五、输出丰富度原则的交互模式落地

这是用户明确点名的一节：原聊天引擎提示词里的「输出丰富性原则」以**字数、篇幅、逐条罗列、零省略**为计量单位；交互模式的交付物是界面，必须把它翻译成"组件、卡片、图表、层数、内容长度"的计量，而且方向是**越多越好**。

### 5.1 原文的丰富度原则（逐字保留在档位主体里）

八份原文都带强丰富度要求，迁移时全部逐字保留：

- 效率 / 专家：`# 输出丰富性原则（最高优先级，全程生效）`，含核心三原则、详尽输出五原则、具体执行标准 6 条（信息充分展开、字数与篇幅、结构层次丰富、禁止内容压缩、多维度覆盖、动态深度调节）。
- 经典：`## 输出丰富性原则（OUTPUT RICHNESS PRINCIPLE）`，6 条执行标准与"禁止压缩"清单。
- 法律 / 研究：核心行为准则里的 `1.2 详尽输出原则（最高优先级）`。
- 信息筛滤 / LLM 评估：核心原则里的详尽输出要求（"零省略、不简化"）。
- 论文转换：字数策略参数（`maintain` / `double` / `triple` / `custom` / `compress`）与输出格式规范。

**这些原文一句没改**。档位主体只追加"计量单位换成界面组件"的适配块，不重写原则本身。

### 5.2 代码层的「丰富度基准（交互版）」

共享层的 ⑤ 段由 `GuncatUiPrompt.richnessForTier(tierRich)` 生成：

- **轻简（`tierRich=false`）**逐字返回 `RICHNESS`，其中数量口径保持原文：典型 8~14 个组件是常态、不是越少越好，但也**不是越多越好**（段总长 3,462 字符）。
- **其余八档（`tierRich=true`）**把这一段替换为 `RICHNESS_TIER_QUANTITY`（段总长 3,462 → 3,597，+135 字符）：
  - **组件与篇幅：越多越好**（"这是本应用的产品特色，不是缺陷"）；
  - 一屏之内尽量把 5 层都铺满，每层 2~4 个组件；**12~20+ 个组件是常态，不设上限**；
  - 能多画一张图、多给一组指标卡、多开一层分节、多写一段展开，就多给；**不要为了"怕多、怕啰嗦"删减任何组件或压缩内容长度**；
  - 同一份数据仍不要原样重复——但"互补"的处理方式是**再补一个维度的组件**，不是删掉已有的。

选择优先级表、分层配方、正反对照示例这些**结构段全档共用**，只有数量口径按档替换。另外 `tierPrime()` 的「丰富度」小节对八档统一写了一句：组件、卡片、图表、分层与每块内容长度**越多越好**，宁多勿少；唯一要求是互补读法。

### 5.3 档位主体里的追加块

八档里有 7 档在原文的丰富度 / 详尽度相关章节之后追加了独立的「丰富度的计量」块（标题与行号见第六节逐档清单）：效率 L126、专家 L120、经典 L85、论文 L246、法律 L55、研究 L59、评估 L50。代表性表述（节选）：

- 效率："12~20+ 个组件是常态，不设上限。能多给一张图……就多给——**不要以'怕多、怕啰嗦'为由删减任何内容**，这是本软件的产品特色。"
- 法律 / 研究："能多开一层分节（`Tabs`/`Accordion`）、多给一组指标卡、多画一张图、多写一段展开，就多给——不要因为'怕多、怕啰嗦'而删任何内容。"
- 评估："「字数优先」「逐条罗列」「零省略」「不简化」在交互模式同样成立：文字进 `TextContent`/`SectionBlock`/`Tabs`，长就分段、分页签，**不压缩**。"
- 论文："论文该有的章节、论证、引用、批注都要在界面里出现，不因'界面要简洁'而压缩。"

信息筛滤档没有另起一块，而是把"组件、卡片、图表、层数、每块内容长度越多越好、宁多勿少"并入顶部「本档位运行环境」的丰富度口径一条；代码层 ⑤ 段已经统一声明 12~20+ 不设上限，主体里不再重复。论文档的计量块同样只写"越多越好 / 宁多勿少"，不重复 12~20+ 这个数字——**上限口径只有一个家（共享层 ⑤ 段）**，这与"一条规则只留一个家"的维护约定一致。

### 5.4 轻简为什么保持「8~14 够用为准」

轻简就是原来的交互模式提示词，产品定位是"一句话一张界面、最快"。它保留 `RICHNESS_LITE_QUANTITY` 的原文口径：典型 8~14 个组件、不是越少越好、但也不是越多越好；`INTERACTIVE_DUTY` 里也是"8~14 个组件是常态"。这是**有意的产品差异**，不是遗漏；`test-core.mjs` 有断言钉住"轻简档保持原样"（`richnessForTier(false) === RICHNESS`）。

### 5.5 边界：越多越好 ≠ 堆砌

丰富度放大只作用于"内容与表达"，下面三条同时生效，避免走向堆砌：

- **互补读法**：同一份数据不要在指标卡、图表、表格里原样说三遍；互补不是删组件，而是补维度。
- **真实数据纪律**：数字必须来自工作区文件 / 工具结果 / 用户输入，宁可用 `Callout` 说明缺口，不能编假数字把界面填满。
- **入口按需给**：操作层（`Form` / `OptionCards` / `Buttons`）只在确实存在"用户大概率会点"的下一步时给，不按轮硬塞。

## 八、维护约定

### 8.1 重新导出

九档导出文件是**生成物，不要手改**；改代码或档位主体后重新生成：

```bash
cd test/guncat-harness && node setup.mjs && node dump-interactive-tiers.mjs
```

- `setup.mjs` 把 `common/` 与 `service/` 的纯逻辑模块镜像到 `test/guncat-harness/gen/`（导出脚本从这里 import 真实模块，保证"导出的就是运行时拼的"）；**改了代码必须先跑它**。
- `dump-interactive-tiers.mjs` 输出 `docs/prompts/interactive-tiers/README.md`、`01-lite.md`~`09-eval.md`，并刷新轻简预览 `docs/interactive-prompt-preview.md`。脚本内有两道自检：① 轻简档组装结果必须与旧四段组装逐字节一致，否则抛错；② 每档"段拼接结果"必须等于 `assemble()` 结果，防止结构与全文分叉。

### 8.2 改原提示词时怎么同步

1. 先改 `entry/src/main/resources/rawfile/` 下的原始提示词（仅聊天引擎用，档位不直接读它）。
2. 把变更同步进对应档位主体 `interactive-tier-*.md`：标题降级规则、`交互模式适配` 标注、锚点改写一致；**不做无标注的大段改写**。
3. 重新导出、跑迁移质量门、更新受影响文档与 `CHANGELOG.md`（有用户可见行为变化时）。
4. 只改档位主体、不改代码时，也建议跑一遍导出，确保导出文件与主体一致。

### 8.3 新增档位

1. 在 `entry/src/main/ets/common/InteractiveTiers.ts` 的 `buildAll()` 里追加一条元数据：`id`（稳定、不可改名）、`name`、`sourceAgent`、`tagline`、`description`、`sourceFile`、`promptFile`、`defaultEffort`、`extraTools`。
2. 按迁移规范写 `entry/src/main/resources/rawfile/interactive-tier-<id>.md`：骨架 = 说明注释 + 本档位运行环境（新增）+ 原文主体（逐字保留、锚点适配）+ 交付前自查（新增）；标题层级 = 删掉原文件的标题型 H1、其余 H1 统一降为 H2、全文 0 个 H1；新增/改写一律带「交互模式适配」标注（各档清单见第六节）。
3. 运行时加载**无需改代码**：`AgentLoader.loadInteractiveTierPrompts()` 遍历 `InteractiveTiers.ALL`，按 `promptFile` 读 rawfile。
4. 工具面**无需改代码**：`ToolRegistry.interactiveWhitelist()` 自动读 `extraTools`；若要新增基础工具，改 `INTERACTIVE_TOOL_WHITELIST`（正表，新工具默认不进交互模式）。
5. 设置页**无需改代码**：九档单选由 `ForEach(InteractiveTiers.ALL)` 生成。
6. 导出**无需改脚本**：`dump-interactive-tiers.mjs` 遍历 `ALL` 自动生成文件与 README。
7. 必须同步改**测试与文档**：`test-core.mjs` 里"九档齐全且顺序固定""八档各有一份主体"等断言按新数量更新；同步更新 `docs/features.md`、`docs/guides/usage.md`、`docs/architecture/interactive-mode.md`、`README.md` 与本说明，并检查新主体的标题保留率/净增等质量门。

### 8.4 迁移质量门（`test-core.mjs`）

跑法：`cd test/guncat-harness && node setup.mjs && node test-core.mjs`。与档位提示词直接相关的门（断言名以脚本为准）：

| 门 | 内容 |

### 8.5 三条硬约定

1. **一条规则只留一个家**：界面语法归 `SYNTAX`、组件选择归 `RICHNESS`、真实数据归 `interactiveTruth()`、交付形态归职责段、专业内容归「档位主体」。不要在档位主体里复述共享层，也不要为了"强调"把同一句话铺到多处。
2. **不改生成物**：发现导出 README / 九份全文有错，改脚本或档位主体后重跑；不要手改 `docs/prompts/interactive-tiers/` 下的文件。
3. **改动看三处**：改共享层要跑轻简逐字节断言；改主体要跑迁移质量门；改工具面要跑 27 + 追加断言。最后跑 `python tooling/docs-check.py --strict` 与 HAP 构建。

## 九、已知取舍与未验证项

1. **token 成本与首答延迟**：专家档系统提示词约 **54,053 tokens**（84,708 字符），轻简约 **10,720 tokens**（21,770 字符）。长提示词直接增加每轮输入 token 成本与 prefill 时间，首答会变慢；重档位适合"值得慢"的任务，日常问答建议留在轻简。**真机 TTFT / 端到端时延尚未做对照测量**，见第 6 条。
2. **token 数是估算**：`PromptBudget.estimateTokens()` 用启发式（中日韩 1 字符≈1 token、连续 ASCII≈4 字符/token、其他非 ASCII≈1 token），与具体模型 tokenizer 存在偏差；导出里的"估算 tokens"只用于量级比较，不应作为计费依据。
3. **上下文窗口被系统性占用**：专家 / 评估档仅系统提示词就占约 5.4 万 / 3.5 万 tokens，留给历史、工具结果与输出的空间相应变小；长任务可能更早触发上下文压缩，压缩后仍会重建同一档位的系统提示词（不会串档）。
4. **源语言选中文版**：四个通用档位有中英两版原始提示词，档位统一用中文版（与交互模式环境语言一致）；英文版继续留给聊天引擎、未改动。英文提问仍可用，但档位主体的方法论是中文表述。
5. **原文段落刻意保留**：mermaid 规范、聊天引擎平台工具说明、`ask_user_question` 提及、文件卡片 / 链接等旧交付词汇仍逐字保留在档位主体里，只在约定锚点用「交互模式适配」块映射（不输出 mermaid、工具映射到真实工具、提问改界面表单）。这是"主体逐字保留 + 可对照"的代价：提示词里存在少量不会在交互模式执行的规则，可能占用模型注意力，但换来原文可审计、可回溯。
6. **真机效果尚未评估**：本次只做了结构、断言与导出层面的验证，**没有任何档位做过真机 A/B 或效果评测**；"档位越重效果越好"不成立，应按任务复杂度选择。重档位是否值得其 token 成本，需要真机数据回答。
7. **缺主体静默回退**：档位主体缺失 / 为空时会静默回退轻简档（代码有意不报错），用户可能只看到"这个档位好像没什么区别"。是否加诊断日志 / 设置页提示，待定。
8. **切档的缓存代价**：系统提示词与工具面都按档位缓存；切档后第一轮请求前缀变化，KV 缓存不命中（首轮更慢）；切回旧档可复用旧缓存。这是"档位可随时切换"的固有成本。
9. **组件清单口径**：组件清单由 `GuncatUiLibrary` 单一事实源生成（导出段 8,712 字符）；"注册组件数"与"提示词清单可见组件数"不是同一个数，两者的区别与当前口径见 3.2 节，组件数量与签名一律以导出文件的组件清单段为准。
10. **导出 README 的组件数量文案**：README 分层表里的组件数量沿用生成脚本中的历史表述，与本文口径（注册 77 / 清单可见 75）不一致；该文案属生成物，由导出脚本维护，不在本说明里手改，组件数量与签名以导出文件的组件清单段为准。
