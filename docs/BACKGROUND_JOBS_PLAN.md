# 后台任务（run_in_background / job_*）在鸿蒙版的可行性与方案

> 状态：**暂缓实施**，本文供评估。审计背景见 `docs/ALIGNMENT_GAP_AUDIT.md` 3.4。

## 一、现状

- `shell` 同步调用：默认 60s、上限 240s；外层护栏 360s。超时即返回 ERROR，**拿不到增量输出，也无法中途 kill**。
- `run_python` 同步调用：默认 30s、上限 180s；超时未中断的调用会继续在后台跑（工具层已有"挂起任务"计数）。
- 电脑版 `run_command` 有 `run_in_background` + `job_list` / `job_output`（读后即弃游标）/ `job_kill`，单会话最多 8 个任务。

**结论：缺的不是"能不能跑"，而是"跑不完时能不能接着看"。** 真机上大任务失败的代价是"重跑一遍"，不是"看不到结果"。

## 二、为什么不能照抄电脑版

1. **内存是硬约束**。VM 常驻 2GB 配置 + 原生 Python 常驻解释器（全库 import 约 1.1~1.2GB）+ 每次工具结果的主线程字符串。
   电脑版的后台任务模型是"8 个进程各留一份输出缓冲"（`WORK_CMD_JOB_BUFFER_BYTES`），换算到手机就是几千 MB 的峰值。
2. **闪退不可捕获**。系统 OOM kill 不产生 JS 异常，用户看到的是应用直接消失（此前 Python 一次分配几百 MB 就踩过）。
   后台任务会显著抬高"同时存在的大对象"数量，把偶发闪退变成高频。
3. **VM 是单核解释执行**（TCI）。并发两个任务不是"更快"，是互相拖慢；`shell` 服务本来就串行化了命令链。
4. **后台保活只覆盖"进程不被挂起"**，不覆盖"内存不被回收"。`BackgroundTaskService` 申请的是 dataTransfer 长时任务，
   它保的是网络/CPU 时间片，不是堆。

## 三、建议方案：单任务 + 落盘游标（不做多任务）

核心思路：**同一时刻只允许一个后台任务**，输出全部落盘，工具只读"游标之后的那一段"。
这样内存峰值与"跑一个前台命令"完全一致，只是把"等"换成了"下次再看"。

### 3.1 接口（与电脑版同名，降低提示词与模型习惯的迁移成本）

| 工具 | 语义 | 手机版特有的约束 |
| --- | --- | --- |
| `shell(..., run_in_background=true)` | 下发命令后立刻返回 `job_id` | 仅当当前无后台任务时接受，否则直接拒绝并给出在跑的那个 id |
| `job_output(job_id)` | 返回**自上次读取以来**的新增输出 | 单次最多 12000 字符（复用 `WORK_SHELL_HEAD_CHARS` 的一半），其余留在文件里 |
| `job_list()` | 列出当前任务与状态 | 最多 1 条（单任务模型），不设"8 个" |
| `job_kill(job_id)` | 终止 | 走已有 abort 链路销毁会话内的执行 |

`run_python` 第一版**不开放**后台：解释器是进程内的，后台执行等于让主线程之外多一个持锁的长任务，
与"OOM 直接闪退"叠加后风险最高；先把 `shell` 这一条跑稳。

### 3.2 实现落点（复用现有机制，改动集中）

1. `LinuxShellService` 已经有 `ipc/<会话>/in|out/<jobId>` 的任务目录契约：
   把"下发 → 轮询 done 文件"拆成两步：下发后立即返回 `jobId`，结果文件由 `job_output` 增量读。
2. 输出文件：`filesDir/linux/ipc/<会话>/out/<jobId>/stdout.log`，按 8KB 追加写；`job_output` 记录
   每个 job 的读游标（内存 + 会话日志），只返回游标之后的部分，读满 12000 字符即停（不一次性把整份读进内存）。
3. 任务状态：`filesDir/linux/ipc/<会话>/out/<jobId>/status.json`（running / exit_code / started_at / command 摘要），
   `job_list` 读它，不做内存表 —— 丢进程也能恢复（重启后按目录重建）。
4. 空闲回收：任务结束 10 分钟后随 VM 一起关机（沿用 `WORK_SHELL_IDLE_SHUTDOWN_MS`）；
   任务在跑时**不关机**，但空闲关机计时器重置。
5. 护栏：后台任务总时长上限（建议 30 分钟）到点自动 kill 并在结果里写明；
   单会话同时只允许 1 个；任务未收尾前 `shell` 的同步调用直接拒绝（避免"一个后台 + 一个前台"抢 VM）。

### 3.3 与"闪退"的关系：三条护栏一起上

1. **单任务**：峰值不叠加（最重要的一条）。
2. **输出落盘 + 游标**：永不把整份日志读进 JS 堆；`job_output` 单次有字符上限。
3. **任务失败不重放**：`shell` 命令不自动重试（现有 `ToolRegistry.setRuntimeConfig(..., maxRetries=0)` 已如此），
   避免"超时 → 重试 → 两个任务同时跑"。

### 3.4 如果连单任务也不放心（保守版）

只做**"超时转后台"**：`shell` 同步等到上限时，不返回 ERROR，而是自动转成后台任务并返回 `job_id`
（提示"已转入后台，用 job_output 继续收"）。模型与用户的心智不变（还是一条命令），
但"跑太久白跑"这件事消失了。数量上永远只有 1 个任务，实现量大约是真后台方案的一半。

## 四、建议的分阶段

| 阶段 | 内容 | 风险 | 量级 |
| --- | --- | --- | --- |
| P1 | 保守版：超时自动转后台 + `job_output` / `job_kill` | 低（同一时刻只有 1 个，且由超时触发） | 1~1.5 天 |
| P2 | 显式 `run_in_background=true` + `job_list`（仍是单任务） | 中（模型可主动并发，靠"单任务拒绝"兜住） | +1 天 |
| P3 | `run_python` 后台（需要解释器侧的锁与生命周期管理） | 高（进程内解释器 + OOM） | +2 天，建议先真机压测 |

## 五、验收清单（P1 起适用）

- [ ] 120 秒的 `sleep` + 大输出命令：`job_output` 分次能读全，内存不随输出增长（DevEco 内存快照对比）。
- [ ] 任务进行中再次 `shell` 同步调用被拒绝，提示明确。
- [ ] `job_kill` 后 3 秒内 VM 内进程消失（`ps` 验证）。
- [ ] 杀进程重启应用：`job_list` 能列出残留任务并标注"已中断"，不误报"运行中"。
- [ ] 连续 20 次"长任务 + 收输出"不闪退（真机 30 分钟压测，观察 RSS 曲线）。
