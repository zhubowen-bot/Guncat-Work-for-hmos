# Preservation Rules And Limits

Read this before editing or repacking a document. These guardrails protect user content, OpenXML relationships, media, formulas, tables, and concise final output.

## Preservation Rules

- Do not run the formatter when the user has not provided a target `.docx`; ask for the target Word file.
- Do not run the formatter when there is no explicit user formatting instruction, valid Word `.docx` template/source-format file, or extractable formatting evidence from another source; ask for target formatting rules or a `.docx` template/source-format file.
- Do not treat non-`.docx` format sources as reliable templates by default, including but not limited to `.pdf`, images, website links, and legacy `.doc`/`.dot`. This skill works best with `.docx` because OpenXML exposes style, numbering, section, header/footer, table, formula, and relationship parts directly. Non-`.docx` extraction depends on OCR, PDF parsing, website extraction, screenshots, Word/Word/预览 conversion, or other tools and may miss or distort styles. Try extraction first, continue when usable formatting evidence exists, stop only when no extractable format requirement exists, and include the non-`.docx` risk plus two alternatives in final notes: upload a native `.docx`/`.dotx` source-format file, or directly provide explicit formatting rules as text instructions.
- Do not describe extracted text rules from non-`.docx` sources as lower priority than fallback. The source container is lower confidence; the explicit rule text is high priority for the properties it states. Fallback fills only properties the text did not state or properties whose source evidence is unsafe/default.
- Do not create separate target-formatting behavior for different source formats. Native `.docx`/`.dotx`, converted `.doc`/`.dot`, PDF, image, website, and text rules must all be fused into `style_spec.json` first, then applied through the same role-map/style-spec route.
- Do not let any non-`.docx` source bypass the conservative evidence chain: explicit/user text rules first, extracted source text rules second, reliable source column detection for fallback variant third, granular fallback last, then QA repair. This applies equally to PDF, legacy `.doc`/`.dot`, images, OCR screenshots, websites, and plain text instructions.
- Do not treat a PDF sample issue, sample article, publisher proof, or PDF format instruction as equivalent to a `.docx` template. It is only a final visual/text result and may contain article-specific layout choices. It does not expose reliable Word style XML, numbering definitions, section breaks, table border XML, formula tab stops, object anchors, or header/footer relationships. Use PDF-derived text evidence when extractable, preferably through 原 PDF 提取脚本（本项目用 search_pdf/pdf_to_images）; use geometry only for single/double-column fallback selection. If no explicit text rule is found, continue with standard fallback and mention the PDF/non-DOCX fallback risk in final notes.
- Do not let PDF-derived rules override explicit user rules or native `.docx` template evidence. PDF visual inference must not identify style roles, role alignment, fonts, sizes, colors, spacing, indentation, tabs, or run-level formatting for `style_spec.json`; only fallback column metadata may be retained.
- Do not let low-confidence visual evidence block fallback baselines. PDF/image/website/OCR/DOC/DOT visual hints may help identify single/double-column fallback only. Fallback must fill all remaining formatting, including Chinese body five-point size, 1.5 line spacing, title/heading spacing, reference indentation, table borders, and equation-centered/right-number layout. Only explicit prose/user rules can lock a different value.
- Do not use website-link visuals, publisher brands, published article pages, production layouts, or Nature/Science-like common practice to infer double-column manuscript format. For website links only, if the website/user text does not explicitly say single-column or double-column, default the fallback variant to single-column and record `website_unspecified_columns_default_single`.
- Do not let PDF left-edge clusters alone trigger double-column fallback. Single-column PDFs can produce several left x clusters from first-line indents, hanging references, centered headings/captions/equations, and formula rows. First require page-level balanced left/right body bands, a real gutter, right-band text-width evidence, and low crossing-line ratio. If sample-issue pages have sparse prose because titles, formulas, figures, tables, or captions dominate, allow a second cross-page aggregate check: stable left and right column starts must recur across multiple pages, pages must contain both starts, the left-column right edge and right-column start must leave a real gutter, and full-width crossing text must stay low. If both checks are weak, default to single-column and record a manual `--body-cols` override hint.
- Do not implement fallback from prose descriptions when bundled OOXML fallback exists. Select `zh_single`, `zh_double`, `en_single`, or `en_double` from `assets/fallback_ooxml_spec.json` and merge its role `pPr_xml/rPr_xml`, `Normal`, body baseline, table three-line XML, and equation baseline first. The older dictionary fallback may only fill fields still absent after this XML merge.
- Do not treat bundled double-column fallback as whole-document double column. For weak/non-`.docx`/blank-carrier sources, Chinese and English double-column fallback must keep title, author, affiliation, metadata, abstract, and keywords in a single-column front section and start double columns at the body section. If no safe body-start split is found, keep the single remaining section single-column and warn instead of making front matter double-column.
- Do not align Chinese `中图分类号`/`文献标志码` metadata with justification or repeated spaces. Whenever the target explicitly contains this pair in one paragraph or adjacent metadata paragraphs, put both fields on one line with one Word tab before `文献标志码`, set a right-aligned tab stop at the computed body text boundary, and set the paragraph alignment to left. This deterministic repair applies to native DOCX and weak-source routes alike unless the user gives a conflicting instruction; do not apply it to unrelated metadata.
- Do not let the bundled OOXML fallback modify native `.docx` template role styles. For native `.docx`/`.dotx` templates, missing style properties may be intentional Word inheritance, so generated role styles must come from user rules, template text rules, representative direct formatting, and template style XML only. Bundled OOXML fallback is allowed for weak non-DOCX sources, blank carriers, and table/equation-specific fallback surfaces.
- Do not confuse that guardrail with ignoring explicit prose rules in native `.docx` instruction templates. If a native `.docx` text rule explicitly locks a role's font or字号 but the role paragraph/style has missing/default paragraph properties, complete only the missing properties from granular fallback. Preserve the locked text-rule font/字号 and do not use the explanatory paragraph's `line="0"`, placeholder indentation, or example spacing as authoritative.
- Do not treat a text rule as locking a whole XML node when it only names one attribute. Merge fallback at property level: `rFonts/@eastAsia` can be locked while `rFonts/@ascii`/`@hAnsi` still come from fallback; `spacing/@line` can be locked while `@before`/`@after` still come from fallback.
- Do not ignore user rules because they are written as OOXML-summary JSON instead of the flat schema. Normalize `summary.pPr.spacing.line`, `summary.pPr.spacing.lineRule`, `summary.rPr.sz.val`, `pPr.spacing`, `rPr.sz`, `summary.pPr.ind`, and `summary.pPr.jc` before deciding whether a rule is explicit. If normalization accepts a field, it has the same priority as a flat `spacing`, `size`, `indent`, or `align` user rule.
- Do not let final notes say "some details used fallback" without clarifying that explicit text-rule properties were preserved. Use wording such as: "来源不是 DOCX，明确文字规则已按优先级采用；未写明的属性由标准兜底补齐。"
- Do not let a blank/carrier DOCX define the fallback language or Word defaults. When the source is `blank_carrier_template`, decide the fallback language from explicit rules first and then the target document text. Use Chinese fallback for Chinese targets and English fallback for English targets. Only use the carrier/template language when both rules and target text are inconclusive.
- Do not preserve blank/carrier `Normal` or `docDefaults` as formatting evidence. Materialize the selected fallback body baseline into target `docDefaults` and `Normal`, and generate role styles from explicit rules plus fallback. This prevents blank Word defaults such as single line spacing `w:line="240"` from overriding Chinese fallback 1.5 line spacing `w:line="360"`.
- Do not let weak-source `Normal` or `docDefaults` disagree with explicit body user rules. If body user rules set `w:spacing w:line="480"` or size `24`, apply those locked body channels to `docDefaults`, `Normal`, and the body role style after fallback merge. Otherwise paragraphs that remain `Normal` can still show the old default line spacing.
- Do not treat legacy `.doc` or `.dot` as a valid OpenXML package or a reliable template/source-format. A `.doc`/`.dot` file has no inspectable `word/styles.xml` package part until conversion, and conversion can produce incomplete or misleading style definitions.
- Do not treat `.doc`/`.dot` conversion as equal to a native `.docx` template. Convert `.doc`/`.dot` to a temporary `.docx` with Microsoft Word when available or Word/预览 otherwise only to extract text and optional column-count metadata. Do not use converted `styles.xml`, direct paragraph/run formatting, support files, headers/footers, or page XML as style evidence. Stop only if no text can be extracted and no fallback route is acceptable, and warn in the final notes.
- Do not let converted legacy `styles.xml` override explicit text instructions or fallback. If most visible converted paragraphs use `Normal`, that is not a style source; the route remains extracted text rules plus standard fallback.
- Do not let converted DOC/DOT shell styles leak unproven visual residues into final role styles. Strip or ignore blue/red/orange colors, underlines, small caps, caps, paragraph borders, shading, frame properties, theme-only heading/reference defaults, and local emphasis unless explicit user/text rules require them.
- Do not treat website links as fully reliable format sources without warning. Extract available website/text evidence. If a website may contain image-based formatting instructions that are inaccessible or hard to parse, record the risk, suggest screenshots of the relevant website images as supplemental evidence in final notes, and continue only when the currently extractable evidence contains usable formatting requirements.
- Do not promote screenshot/image/website/PDF visual styling to Word formatting unless the text explicitly states it. Visual evidence from these sources may identify only reliable single-column or double-column fallback choice, except website links where unspecified column layout must default to single-column. Do not visually infer paragraph roles, role alignment,字号/point size, fonts, bold/italic, colors, underline, indentation, line spacing, paragraph spacing, tabs, reference hanging indent, or run-level details.
- Do not preserve low-confidence visual `both`/`justify` alignment for front-matter title/author/affiliation roles. Long titles and author lines are often misread as justified by PDF/image coarse screening; drop visual-only alignment entirely and use explicit text rules or fallback.
