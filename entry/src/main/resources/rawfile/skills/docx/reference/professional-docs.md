# 专业文书写作规范（Professional Docs）

面向用户明确要"公文/合同/报告/新闻稿/技术交底书"等专业文体时，给出结构骨架与 Doc JSON 落地建议。
**先判断文体再动笔**；每种文体给出：结构、语言、Doc JSON 建议、能力边界。

## 0. 来源与优先级（参考 Doubao word 各文体指南）

- 公文/党建材料：优先移植 Doubao `government-and-party-documents.md` 的文种速览、通用格式原则与红头/白头模板规则。
- 合同/协议：优先移植 Doubao `business-agreements.md` 的文书类型分流、模板优先级与无模板起草规则。
- 专业领域文书：优先移植 Doubao `professional-domain-documents.md` 的原则（专业依据、禁止编造、格式以法定/组织模板优先）。
- 分析/研究报告：优先移植 Doubao `strategy-and-analysis.md` 的核心问题—证据—判断框架。
- 法律备忘录/战略备忘/系统设计：保留此前 ChatGPT 模板移植（用户明确允许保留 GPT 来源）。
- 格式优先级：用户明确要求 > 有效模板/组织规范/法定文种要求 > 本文件补充规则 > writing-taxonomy 一般格式。

## 通用规则

- 标题是结论或文件主题；H1 用"一、"，H2 用"（一）"或"1.1"，全文统一一种编号体系。
- 段落一段一个观点；正式文书用书面语，不用口语/AI 腔。
- 表格/图片必须加题注与来源；没有来源的数据不写。
- 当前渲染器不支持页眉页脚/页码/脚注/批注/多栏/嵌入字体；需要这些时明确说明并给近似替代。
- 禁止编造主体身份、金额、日期、案号、法律条文编号等事实；未知字段用待确认占位。

## 1. 公文 / 红头文件（参考 Doubao government-and-party-documents）

**文种先判断**：上行文（请示/报告）、平行文（函）、下行文（通知/批复/决定等）、信息类（简报/专报）、讲话稿、面向社会公开文书、法人对公文书、思想汇报。**不要用相近模板替代不对应文种。**

**通用格式原则（权威规则）**：

- 用纸 A4（210×297mm）；天头 37mm±1mm、订口 28mm±1mm、版心 156×225mm。
- 文字默认黑色；中文标点必须用全角中文引号，严禁英文标点。
- 标题：2号小标宋体；正文：3号仿宋体；一级标题：3号黑体；二级标题：3号楷体；三级及以下：加粗 3号仿宋。
- 行距固定值 28～30 磅（推荐 28 磅）；正文每段首行缩进 2 字符，段首不添加文本空格。
- 层次序数统一用"一、 → （一） → 1. → （1）"；同一级别用同类序号。
- 严禁无序列表（空心圆/实心圆/星号/短横）；数字、字母随所在要素字体，前后不加空格。
- 抬头顶格书写、落款居右书写，两者不缩进；落款不得单独出现在末页，必须与正文最后一段同页。
- 标题不要拆词组换行；标题与正文之间可空一行，正文各段之间不要多空行。
- 附件另面编排；图片/表格须先在正文以"（见图1）"引出，图/表下方居中注明"图1：xxx"。
- 红头：发文机关名称居顶、红色小标宋、下置红线，单行显示；`字数 × 单字宽度 < 版心宽度 156mm`，超出必须缩小字号而非折行。
- 不生成真实印章图样。

**Doc JSON 建议（白头近似，正式红头需外部套版）**：

```json
{"title":"关于开展……工作的通知","author":"××单位","date":"2026-09-17","style":"default","blocks":[
  {"type":"paragraph","text":"各相关部门："},
  {"type":"heading","level":1,"text":"一、总体要求"},
  {"type":"paragraph","text":"……"},
  {"type":"heading","level":2,"text":"（一）……"},
  {"type":"paragraph","text":"……"},
  {"type":"paragraph","text":"特此通知。"},
  {"type":"paragraph","text":"××单位"},
  {"type":"paragraph","text":"2026年9月17日"}
]}
```

**能力边界**：当前渲染器无红头、发文字号、版记、页码、页眉页脚；用"标题 + 正文 + 落款"近似并明确告知用户正式红头文件需在 Word/WPS 套版。

## 2. 合同 / 协议（参考 Doubao business-agreements）

**先分流文书类型**：

- **合同**：以交易/服务/采购/建设/租赁/买卖/合作交付等权利义务交换为核心，需要主体、标的、价款、履行、验收、违约、争议解决、生效签署。
- **协议**：框架合作、补充约定、会议一致意见、项目协作安排；不等于低规格。
- **普通约定**：欠条、收据、低复杂度合作备忘，只写清真实约定，不机械套长合同。

**模板优先级**：用户模板 > 官网示范文本（国家市场监督管理总局合同示范文本库 `https://htsfwb.samr.gov.cn/`，下载 Word 版本并记录标题/发布机关/版本/URL）> 无模板起草。

- 有用户模板：复制后**原位填写**，保留编号和样式，不得只提取字段后重建；核验模板中法律名称/条文编号/机构名称是否现行有效，发现疑似废止/修订时不得自行替换，记录待核验。
- 无模板：按真实法律关系保留必要模块（主体与资格、鉴于条款、标的、价税与支付、履行期限地点方式、交付与验收、双方权利义务、变更解除、违约责任、不可抗力、保密/知识产权/数据处理、通知送达、争议解决、生效签署、附件）。
- 条款写清"适用条件—主体—动作或标准—期限—不履行后果"；未触发的通用条款不机械加入。

**结构**：

```
标题：××合同/协议
甲方/乙方（当事人信息：名称/统一社会信用代码/地址/联系人）
鉴于条款（必要时）
正文条款（"第一条、第二条……"为主层级；条内再按（一）/1.，不混用"四、"和"4.1"）
签署区（名称/授权代表/日期，只提供文字与留白）
```

**Doc JSON 建议**：当事人信息用 table；条款用 H1/H2 + paragraph/list；金额/日期用加粗行内格式；签署区用段落留白。

**能力边界**：不承诺法律效力审核；不生成印章/签名/已签署状态；无签章图片时用文字占位说明"此处由双方盖章"；合同类任务建议配合 law 技能做风险视角。

## 3. 研究报告 / 咨询报告（参考 Doubao strategy-and-analysis）

**核心逻辑**：围绕"核心问题 → 证据 → 判断"组织；不要逐项报数，不要堆图表。先确定报告目的落点：

| 报告目的 | 内容重点 | 最终落点 |
|---|---|---|
| 描述现状 | 当前情况与值得关注的变化 | 帮助读者形成清晰认识 |
| 诊断问题 | 主要问题与成因 | 明确问题及改进方向 |
| 探索情况 | 初步发现与可能解释 | 提出值得继续验证的问题 |
| 评估效果 | 按既定目标判断实际表现 | 形成有依据的评估结论 |
| 支持决策 | 比较不同选择及其影响 | 给出推荐意见和适用条件 |
| 预测趋势 | 根据现有证据判断未来变化 | 形成有条件的趋势判断 |

**结构**：

```
封面（title/subtitle/author/date）
目录（≥8 块，动态目录优先）
摘要（结论先行）
H1 研究背景与目的
  H2 背景 / H2 目的与范围
H1 研究方法与数据
  H2 方法 / H2 数据来源与口径
H1 核心发现
  H2 发现一（结论 + 证据表格/图表）
  H2 发现二…
H1 结论与建议
  H2 结论 / H2 建议 / H2 风险与局限
H1 附录：来源与口径
```

**证据呈现规则（权威）**：

- 每个图/表必须回答一个独立问题；同一判断只选一种主证据形式（趋势/差异用图，精确查数用表，明细进附录）。
- 图题在图下（"图 1　图题"），表题在表上（"表 1　表题"）；图后紧跟"数据来源："、期间与口径；来源格式：作者/机构：《标题》，发布方，发布日期，页码/章节，URL（访问日期）。
- 图表选型：时间变化用折线（≥5 个连续时点）、对象比较用条形（≥3 个对象）、构成用堆叠条形/少量饼图、变化拆解用瀑布图。
- 配色：主色 `#1A2B4A` 藏青色阶 + 中性灰 + 单点强调 `#C8861A`/`#B84C3A` 二选一；禁止彩虹色、渐变、3D、投影、默认蓝色 Heading。
- 章节编号如无特殊要求用 `1 → 1.1 → 1.1.1`。

**Doc JSON 建议**：`cover:true` + `toc:true` + academic/default；证据用 table，图片用 write_svg 生成后引用；来源放 caption 或附录表。

## 4. 新闻稿 / 宣传稿

**结构**：

```
标题（结论/卖点）
副标题（可选）
导语（一段：时间/主体/事件/结果）
正文（2~4 段：背景 → 过程/亮点 → 意义）
引语（quote：负责人/专家原话）
结尾（下一步/联系方式）
```

**Doc JSON 建议**：title + 段落 + quote；避免表格（新闻稿以 prose 为主）；如有数据，用加粗或一句话，不用大表格。

## 5. 技术交底书 / 专利初稿（参考 Doubao professional-domain-documents）

> 专业领域文书原则：专业性是首要标准；所有重要内容须能回答"依据什么事实、遵循什么专业标准、为什么得出这一判断"。用户有明确模板/法定格式/组织规范时，优先按模板执行；本结构仅为无模板时的落地方案。

**结构**：

```
H1 发明名称
H1 技术领域
H1 背景技术（现有问题）
H1 发明内容（要解决的技术问题 / 技术方案 / 有益效果）
H1 附图说明（可选：图1 结构示意…）
H1 具体实施方式
H1 技术效果对比（table：现有 vs 本发明）
```

**Doc JSON 建议**：academic 样式；技术方案用有序列表分步骤；对比用 table；示意图用 write_svg 生成并引用。

## 6. 法律备忘录（Legal Memorandum，参考 ChatGPT Legal Memorandum 模板）

**结构**：

```
LEGAL MEMO
To / From / Date / Re（表格或键值段落）
Background（事实与背景：主体、文件、事件时间线；区分事实与假设）
Analysis（控制性条款原文 → 最有力解释 → 可选路径 → 对比与推荐）
Conclusion（建议、负责人、期限、升级触发、fallback）
```

**Doc JSON 建议**：标题用 title；To/From/Date/Re 用 table（`字段/内容`）；Background/Analysis/Conclusion 用 H1 + 段落；引用的控制性条款用 quote/引用块。

**要点**：模板槽位不硬填——没有真实事实时保留 `[待补充]` 并告知用户，禁止编造案号/条款。

## 7. 战略备忘录（Strategy Memo，参考 ChatGPT Strategy Memorandum 模板）

**结构**：

```
Strategic decision or question
1. Purpose and Recommendation（目的 + 推荐结论；Recommendation in Brief）
2. Strategic Context（现状、客户信号、竞争；2.1 The Opportunity）
3. Options Analysis（3.1/3.2/3.3 各选项：收益/成本/约束/风险；3.4 加权决策矩阵）
4. Recommended Path and Conditions（4.1 条件与触发；4.2 风险）
5. Next Steps（负责人—动作—时间）
6. Financial and Strategic Implications（6.1 保留可选性；6.2 什么会改变推荐；6.3 排期）
Appendix — Supporting Notes
```

**Doc JSON 建议**：default 样式；标题层级按 1./2./3.；选项对比用 table（`选项/时间价值/执行风险/战略匹配/推荐`）；加权矩阵用 table；风险用 table（`风险/可能性/缓解`）。

## 8. 系统设计文档（System Design Doc，参考 ChatGPT System Design 模板）

**结构**：

```
1. Abstract（问题、目标系统、边界/依赖/保证）
2. Goals and Non-Goals
3. Background and Problem Statement
4. Proposed Architecture（架构图 + Core components）
5. Request Lifecycle（请求进入→校验→处理→持久化→下游→完成）
6. API and Data Contracts（Primary data contract / Contract guarantees）
7. Consistency, Idempotency, and Replay
8. Security and Privacy Considerations
9. Operational Readiness
10. Alternatives Considered
11. Open Questions
12. Decision and Next Steps
```

**Doc JSON 建议**：academic/default；架构图用 write_svg 生成并引用；API/数据契约用代码块或 table；Open Questions 用列表；每个 section 保持 H1 编号一致。

## 从专业文书到 Doc 的步骤

1. 识别文体（公文/合同/报告/新闻稿/交底书/法律备忘录/战略备忘/系统设计）→ 套上面骨架。
2. 收集事实与数据：来自用户材料/工作区文件/检索结果，禁止编造；模板槽位没有真实数据时保留占位说明。
3. 写 Doc JSON（长文用 doc_file 分块写）。
4. 生成后 `read_docx` 抽查结构；明确告知哪些正式格式（红头/页码/签章）需要外部套版。
