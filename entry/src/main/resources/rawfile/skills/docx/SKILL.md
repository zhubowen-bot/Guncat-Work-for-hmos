# Word 文档制作与编辑（V3）

> V3 把“文档”改成“门”：全量加载、前置提问、自检报告都是不可跳过的硬门，均有可核对产出物。**对外契约不变**：仍只通过 `write_docx(path, doc | doc_file | markdown, title?, style?)`、`read_docx(path)`、`edit_docx(path, ops)` 完成制作、读取与编辑。

## 0. TL;DR 铁律（优先级最高，冲突时以本节为准）

1. **[铁律] 每次接到新 Word 指令或新附件后，第一个工具调用必须是 `load_skill("docx")` 全量加载**。`load_skill("docx")` 会一次返回 SKILL.md + 全部 reference（doc-dsl / design-guide / document-blueprints / professional-docs / chatgpt-design-presets / troubleshooting）。禁止只读 SKILL.md 后挑读 reference，禁止跳过、中途截断或凭记忆继续。
2. **[铁律] 新建文档（工作流 A）动手前，必须先调用一次 `ask_user_question` 前置提问**：文档类型、用途/读者、篇幅、格式要求、素材附件一次问全。用户已提供全部关键信息或明确说“不用问/直接做”时才能跳过，且必须在最终总结记录假设。
3. **[铁律] 交付前必须产出可核对的自检报告**：用 `read_docx` 回读核对，写入 `docx_qa_report.md`，并在最终总结附 `## Word 交付自检报告` 摘要。没有报告不视为完成。
4. **[铁律] 强附件/信息遵循**：公文、论文、法律、科研等严谨场景必须忠实于用户材料原文，禁止编造、扩写或自行补全关键信息；缺失信息用占位符明确标出。
5. **[铁律] 模板优先与最小改动**：用户给了模板/已有文档时，模板与原文是最高约束；原位填充、局部修改，不整篇重写、不另起一套设计系统。

## 1. 规则分级与冲突裁决

| 级别 | 含义 | 违反后果 |
|---|---|---|
| **铁律** | 任何情况下不可跳过，除非用户显式覆盖 | 任务未完成，回到对应步骤补齐 |
| **强规则** | 必须遵守；与用户明确要求冲突时以用户为准 | 视为质量问题，在自检中列出并修复 |
| **建议** | 默认应遵守；有充分理由时可偏离 | 偏离时在自检报告说明理由 |
| **软参考** | 帮助判断，不强制 | — |

**冲突裁决程序（按此顺序，不自行选阻力最小路径）**：

1. 用户当前明确指令 > 用户历史明确指令 > 模板/品牌规范 > 本技能铁律 > 强规则 > 建议 > 软参考。
2. “默认不打断”与“不确定项一次问清”冲突时：**新建文档走“前置提问门”（铁律），编辑/读取/模板填充走“不打断”**；按场景路由分流，不并存。
3. “忠实原文”与“补全信息”冲突时：以用户材料为准，缺失/不确定用占位符与说明，不编造。
4. “模板原位填充”与“重建更精致”冲突时：用户给了可编辑模板则原位填充；只有“格式参考”（PDF/图片/不可编辑附件）才用工作流 A 重建。

## 2. 全量加载门（硬门，不可跳过）

- **每次新指令/新附件后的第一个工具调用**：`load_skill("docx")`。若之前已加载但中间发生了上下文压缩/新用户消息，也重新加载一次。
- `load_skill("docx")` 返回内容应包含下列文件清单；缺少任一文件或明显被截断视为加载失败，需重试：
  - `SKILL.md`（本文）
  - `reference/doc-dsl.md`
  - `reference/design-guide.md`
  - `reference/document-blueprints.md`
  - `reference/professional-docs.md`
  - `reference/chatgpt-design-presets.md`
  - `reference/troubleshooting.md`
- **禁止**：只读 SKILL.md 后说“参考文件按需读”；禁止用 `load_skill("docx","reference/xxx.md")` 替代全量加载（个别文件可在全量之后用于精读，但不能代替）。
- 文档需要插图/示意图时还需 `load_skill("svg")`，按 svg 技能规范生成并 `view_image` 预览。

## 3. 前置提问门（新建文档，硬门）

**新建文档前必须调用一次 `ask_user_question`**，把下列问题合并为一次提问（不要挤牙膏）。由于 `ask_user_question` 是单问题工具，请把各项合并为一段 question 文本；`options` 可提供类型/风格候选。

| # | 问题 | 示例/选项 | 默认假设（用户取消回答时用） |
|---|---|---|---|
| 1 | **文档类型**是什么？ | 报告 / 方案 / 会议纪要 / 合同 / 公文 / 论文 / 操作手册 / 简历 / 其他 | 按主题合理推断 |
| 2 | **用途与主要读者**？ | 汇报 / 决策 / 存档 / 对外发布 / 内部 | 按上下文推断并在总结说明 |
| 3 | **篇幅/详略**？ | 短（1~2 页）/ 中（3~6 页）/ 长（7 页以上，含封面目录） | 按内容量合理扩写，避免过短或注水 |
| 4 | **格式要求**（目录/封面/样式/表格/图片）？ | default / academic / minimal；是否要目录封面 | 默认按文体选最合适样式 |
| 5 | 有没有**素材/附件/模板**需要我使用？ | 有（列出路径）/ 没有 | 用工作区已有资料，禁止编造 |

- 用户已经提供了以上全部信息，或明确说“不要问，直接做”，可跳过提问，但必须在最终总结写“采用假设：类型/用途/篇幅/格式”。
- **编辑已有文档、读取分析、模板填充场景不触发前置提问**；只有真正影响方向的硬阻塞（附件打不开、意图矛盾）才问。

## 一、适用边界与载体路由

### 什么时候使用本技能

- 用户明确要求交付 Word / `.docx` 文件。
- 用户提供 Word 文件作为模板，要求基于它制作新文档。
- 用户提供 Word 文件要求修改编辑并交回修改稿。
- 用户需要正式文书、合同、公文、论文等有格式排版要求的写作。

用户明确要 `.docx`/Word、给了 Word 模板/要基于 Word 修改时才走本文档；否则不要默认造 Word。

### 载体路由（参考 Doubao word：先判断要不要用 Word）

| 体裁 | 典型场景 | 默认载体 |

| 党政公文/正式文书 | 党政机关、事业单位、法人向党政部门提交的正式文书、党建材料、思想汇报 | **Word** |

| 媒体/传播 | 公众号推文、小红书图文、邮件、口播稿、分镜脚本、标题 | 在线文档/文本 |
| 创意写作 | 网文、小说、剧本、故事大纲 | 在线文档/文本 |
| 品牌营销 | 营销策划、产品上市、活动战役、种草 | 在线文档 |

## 二、场景路由

先识别每个输入是目标文档、可编辑模板、内容来源还是格式参考，再按最终交付物判断新建、编辑或模板填充。读取不是与新建/编辑互斥的分支。

| 场景 | 判定 | 执行入口 |
|---|---|---|
| 新建文档 | 无已有 DOCX，或用户明确从零生成 | 工作流 A |
| 编辑已有文档 | 修改意图唯一指向已有 DOCX，并要求交回修改稿 | 工作流 B |
| 模板填充 / 按模板新建 | 用户提供可编辑 DOCX 作为模板或底稿 | 工作流 C |
| 格式参考 / 仿制样式 | 附件只是视觉或结构参考（如 PDF、图片、不可编辑附件），或用户只要“照这个样式做” | 工作流 C 的“格式参考”路径 |
| 读取 / 分析 | 需要先获取内容与结构，再决定后续动作 | `read_docx` 后按需进入 A/B/C |

多个 DOCX 无法唯一确定目标，或“修改原稿”和“按其另建”会带来实质不同的交付物时，先澄清；其余小歧义按保守、少改动的方向处理。

## 三、通用流程：需求 → 规划 → 生成/编辑 → 验收

1. **全量加载**：`load_skill("docx")`（§2）。
2. **理解需求与附件盘点**：确定写作类型、写作目的、作者/主体、主要读者、交付物，以及用户明确要求和排除项。用户提供的附件必须逐一盘点，不静默忽略；必要时用 `write_file` 把附件角色记录为 `attachment_purpose.md`。
3. **规划内容与格式**：复杂或强附件任务先读全附件，再写 `outline.md`；模板任务写 `template-plan.md`。明确标题层级、目录、封面、页码、表格和视觉元素，并确定写作风格。
4. **生成/编辑**：按场景路由进入工作流 A / B / C。
5. **验收交付**：回读全文、检查结构与格式，发现问题修复后重新复验受影响部分；写 `docx_qa_report.md` 并在最终总结附自检摘要。

> **强附件与信息遵循**：公文、论文、法律、科研等严谨场景属于强附件和信息遵循类型，必须忠实于用户材料原文，禁止编造、扩写或自行补全关键信息；缺失信息用占位符明确标出。

## 工作流 A：新建文档

1. **前置提问**：`ask_user_question`（§3）。收到回答后确定类型、用途、篇幅、格式、素材。
2. **先定结构**：封面(可选) → 目录(≥8 块长文用) → 分级标题组织章节 → 正文/列表/表格/图片。标题是结论（“上半年营收 +18%”），正文每段一句话观点 + 论据。
3. **规划内容**：复杂任务或需要引用多个附件时，先用 `write_file` 写轻量 `outline.md`，明确章节、事实依据、重点内容和需要保留的附件信息；没有把握前不要直接写 Doc JSON。
4. **写 Doc JSON**。速查最小例：

```json
{"title":"Q2 经营分析报告","author":"经营分析组","cover":true,"toc":true,"blocks":[
 {"type":"heading","level":1,"text":"一、总体经营情况"},
 {"type":"paragraph","text":"上半年营收 **1.2 亿元**，同比 *+18%*，主要来自华东区。图 1 展示了月度趋势。"},
 {"type":"image","src":"photos/trend.png","caption":"图 1 月度营收趋势（来源：财务中台）","width":0.8},
 {"type":"heading","level":2,"text":"1.1 分渠道表现"},
 {"type":"table","headers":["渠道","营收","同比"],"rows":[["线上","7,000 万","+22%"],["线下","5,000 万","+11%"]]},
 {"type":"list","ordered":false,"items":[{"text":"直播带货 GMV 2,300 万","level":0},{"text":"新开门店 12 家","level":1}]},
 {"type":"quote","text":"增长的本质是复利。"}]}
```

5. **生成**：≤20 块直接 `write_docx` 传 `doc`；更长先 `write_file("doc.json", …)` 分块写好（后续 `append_file` 续写），再 `write_docx` 传 `doc_file:"doc.json"`。
6. **无模板创建要点（参考 Doubao word）**：
   - 用户没有明确要求目录时，默认不生成目录。
   - 注意编号：不要出现自动编号与文本编号重复。
   - 不要因为分段写入出现“XXX续”这类不正式的分节标题。
   - 正文字体字号、同一层级标题字体字号、表格颜色保持统一；严肃场景避免颜色跳跃或过度鲜艳。
   - 数字体系前后一致，严肃场景尽量使用中文数字。
7. **自检 + 写报告**（生成后必做，见 §交付前自检）：`read_docx` 回读核对；写 `docx_qa_report.md`；有问题用 `edit_docx` 修正或改 doc 后重新导出并复验。

> 常见 Word 文档（商务报告/方案/会议纪要/论文/操作手册）的结构蓝图、公文/合同等专业文体规范、ChatGPT 官方设计预设，均已随 `load_skill("docx")` 全量加载；需要细节时可直接精读对应 reference。

## 工作流 B：编辑已有文档

1. `read_docx(path)` 读回源（外来文件注意提示中的近似导入说明与抽取的图片清单）。
2. 小改：`edit_docx` 用 `replace_text`（全文改词）/`update_block`（改单块）/`add_block`/`delete_block`/`move_block`。
3. 换风格：`edit_docx` 传 `{"op":"set_style","style":"academic"}`；改封面/目录开关用 `set_cover`/`set_toc`。
4. **最小改动原则（参考 ChatGPT documents）**：用户给的是已有文档时，先拿当前源，做局部替换/增删，不要整篇重写；保留原有结构，只有用户明确要求重构时才做整体重写。修改意图能唯一指向该 DOCX 并希望交回修改稿时，不要因为用户没说“原路径”就默认重建。
5. 外来文件改前会自动备份 `*_原版备份.docx`，不要删它。
6. 编辑完成后同样执行回读 + 写 `docx_qa_report.md`（极小文字替换可精简报告，但最终总结仍需附自检摘要）。

## 工作流 C：模板 / 占位符填充与模板新建

### 判定：可编辑模板 vs 格式参考

- **可编辑 DOCX 模板/底稿**：模板是必须继承的输出底稿，优先原位填充，不重建整份模板。
- **PDF、图片或不可编辑附件**：只能作格式参考；用工作流 A 重建，不得声称已在模板副本中填写。
- 用户给的是 DOCX 但明确说“照这个样式/结构做”而非在原文件上填写：按下面的“格式参考/仿制模板”处理。

### 可编辑模板填充步骤

1. **完整读模板**：`read_docx(path)` 读模板，区分固定内容、示例内容、占位内容和真实已有内容。
   - 固定内容：原样保留（页面设置、Logo、文号格式、固定说明、签署结构等）。
   - 示例内容：只用于说明格式，按任务替换或删除。
   - 占位内容：填入真实内容、明确留白或删除，不得遗留无意义占位文字。
   - 真实已有内容：按用户要求保留、更新或删除，不因其出现在模板中就默认沿用。
2. **制定模板计划**：可写 `template-plan.md` 或在上下文中记录表格：目标区域 | 内容依据 | 定位方式 | 编辑方式 | 必须保留 | 验收条件。模板中的示例文字、虚构数据不是事实来源。
3. **原位编辑**：模板里有 `{{字段}}`/`【待填】`/`TODO` 时，用 `edit_docx` 的 `replace_text` 逐个替换；内容区域变化用 `update_block`/`add_block`/`delete_block`/`move_block`。不要承诺 Word 邮件合并/域填充。
4. **只改计划范围**：未计划修改的页面设置、样式、编号、表格、图片、页眉页脚、分节、书签等保持不动。新增段落/表格行/图注时，优先复制最近的同类结构并继承样式。
5. **容量与风格控制**：新内容过长时，优先精简表达或在同类结构中扩展；只有原结构确实无法承载时才调整必要内容区域，不重建整份模板，也不另起一套与模板无关的设计系统。
6. **回读验证**：每完成一组修改就回读对应区域，确认内容写入正确位置、格式得到继承、示例内容已清理；全部完成后写 `docx_qa_report.md` 验收。

### 格式参考 / 仿制模板

用户给了一份 docx 说“照这个样式/结构做”：先 `read_docx` 读模板，**分别提取结构与风格**——结构：章节划分/封面目录/表格图片位置；风格：标题层级、正文密度、配色（外来文件近似导入，样式细节看文字/排版描述）。再用工作流 A 用 Doc JSON 重建。改完要保留模板的**内容完整性**：章节齐全、数据一致。

> **模板优先于通用预设**：只要用户提供的模板控制新文档，就按模板的结构和视觉系统执行；不要在没有用户要求时套用通用设计预设或默认样式覆盖模板。

## 能力边界（重要：不要承诺做不到的功能）

**支持**：分级标题(H1~H6)、正文/列表/表格/图片/引用/代码块/公式(OMML)/封面/目录(Word TOC 域，打开后右键“更新域”生成)/分页/分隔线；三种样式预设；图片支持工作区路径、data URL、http、svg 自动栅格化。

**不支持**（用户要求时**明确说明做不到**，并给替代方案）：
- 修订/批注（track changes/comments）
- 页眉页脚、页码、水印、脚注尾注
- 自动更新目录（我们生成的是 Word TOC 域；打开后需在 Word 中右键“更新域”生成页码，不能承诺打开即已自动填好）
- 邮件合并、宏、VBA、文档保护/密码、嵌入字体
- 复杂分节（不同章节不同页边距/纸张方向）、多栏排版
- 文字环绕的浮动图片（只支持行内插图）

遇到这些需求：说明“当前版本不支持 X，已改为 Y（近似替代）”或用纯文本表达（如脚注改为括号注）。

## 块速选

| 块类型 | 何时用 |
|---|---|
| heading(1~6) | 章节标题（自动按级别区分字号：H1 22pt → H6 12pt，黑体加粗） |
| paragraph | 正文段（12pt 宋体，1.5 倍行距，首行缩进 2 字符） |
| list | 要点列表（ordered:true 有序 / false 无序；条目 level 0/1 两级缩进） |
| table | 结构化数据（≤20 列；首行为表头，自动加底色） |
| image | 插图（src 工作区路径/data URL/http；width 0~1 页宽比例；caption 题注） |
| quote | 引用/金句（左侧竖线样式） |
| code | 代码块（等宽字体 + 灰底） |
| divider / pagebreak | 分隔线 / 分页 |

行内格式（在文本字段里直接用）：`**粗体**` `*斜体*` `` `代码` `` `[链接](url)` `![说明](src)` `$公式$` `~~删除线~~`。

字段级语法（必填项、table/image 全字段、样式预设）：`reference/doc-dsl.md`（已随全量加载包含）。

## 排版规范（摘要，全文见 reference/design-guide.md）

- **标题是结论**：H1 写结论句（“营收 +18%”），不用“经营情况”这类空泛词；H2/H3 层层递进。
- **段落**：一段一个观点；长文每章 3~6 段，不要一段塞满整屏。
- **表格**：数据必须来自工作区资料，加 caption 注明来源；超过 10 行考虑拆表或只列关键指标。
- **图片**：不凑数——没有合适图片就用纯文字，好过无关配图；图片必须真实存在且清晰。
- **禁用 AI 腔**（“赋能”“闭环”“综上所述”“不是X而是Y”）；用具体名词和数字。
- 默认样式 default（蓝色标题）适合商务报告；academic（黑标题、素净）适合论文/学术；minimal（灰标题）适合内部备忘。

### 格式统一性（参考 Doubao word）

- 正文字体字号必须统一，同一层级标题字体字号统一。
- 表格样式颜色尽量统一，不出现颜色跳跃或过度鲜艳；严肃场景（政务公文等）尤其克制。
- 自动编号与手工编号不得重复；分节标题不要出现“XXX续”。

### 表格设计硬约束（参考 ChatGPT documents）

- 不要用固定行高截断文字，允许行随内容扩展。
- 单元格内边距和行距要充足，文字不要“贴”在边框上。
- 列宽按内容设计：短字段（编号、日期、状态、金额）列紧凑，长文本列宽；避免所有列默认等宽。
- 短值/状态/数字通常居中，叙述性长文本左对齐；整体保持一致的垂直居中。
- 表格与上下段落之间留白，题注和表格尽量保持在一起。
- 不要把普通 prose 塞进单元格；单元格变成整段话时改回段落/列表/引用。

## 文档形态选型（动笔前先决定“用什么承载”）

参考 ChatGPT documents skill 的 form-factor 原则：**先按信息类型选形态，再写内容**，不要一律“标题+大段文字”。

| 信息类型 | 首选形态 | 什么时候换 |
|---|---|---|
| 叙述/背景/理由 | prose 段落 | 出现可扫描的并列项时改列表 |
| 决策/建议/关键结论 | 段首加粗 lead + 简短理由 | 一句能说清就用一句话 |
| 步骤/流程/操作 | 有序列表 | 步骤带负责人/状态时考虑表格 |
| 并列因素/要求/优缺点 | 无序列表 | 需要逐项对比时改表格 |
| 待办/验收/检查项 | 清单 | 行数很多时分节 |
| 定义/元数据/键值对 | 定义列表（`术语：解释`） | 数量多改表格 |
| 重复结构记录/预算/矩阵 | 表格 | 单元格变成整段话时改回 prose/list |
| 表单/问卷 | 表单布局（字段、分区、作答空间） | 需要固定行列响应结构时用表格 |
| 警告/注意/约束 | 引用块 | 需要强视觉分离时加粗框（quote 近似） |
| 证据/引用/来源 | caption + 文末来源表 | 少时直接括号注 |

**表格门禁**：只有真正“行×列可比较/可查询”的数据才用表格；不要把 prose 塞进单元格。若表格里出现大段句子，就改为段落/列表/引用。相邻两个以上表格检查是否至少一个该换成列表/段落。

**编辑任务最小改动**：用户给的是已有文档时，先 `read_docx` 拿当前源，做局部替换/增删，不要整篇重写；除非用户明确要求重构。
